This document records the implementation of Assignment 5 for the CampusEats Orders service. The work covers correct HTTP verbs, query-based reads, non-CRUD actions, request and response headers, authentication, CORS, caching with ETags, conditional updates, rate-limit signalling, and retry protection. The service is implemented in Python using a lightweight WSGI setup without external runtime dependencies.

1. HTTP Operations and Method Design

1.1 CampusEats endpoint matrix

OperationHTTP requestSafeIdempotentImplementation detail
Browse orders GET /orders?status=&sort=&page=&pageSize= YES YES Filtering, ordering and pagination are supplied through the query string. The request only reads server state.
View one order GET /orders/{orderId} YES YES The representation carries an ETag and cache policy and can be requested conditionally.
Place an order POST /orders NO NO* Creates a new resource and returns 201 Created together with its Location. The Idempotency-Key makes retries safe.
Update delivery address PATCH /orders/{orderId} NO YES Only the requested modification is applied. If-Match prevents an older representation from overwriting a newer one.
Remove an order DELETE /orders/{orderId} NO YES Successful deletion produces 204 No Content and is guarded with If-Match.
Ask for cancellation POST /orders/{orderId}/cancellation NO NO Cancellation is an action rather than ordinary CRUD, so it is represented as a POST sub-resource and returns 202 Accepted.
Check allowed methods OPTIONS /orders/{orderId} YES YES Returns the Allow header and also participates in browser CORS preflight handling.
Method override: A restricted client that cannot transmit PATCH or DELETE may use POST together with X-HTTP-Method-Override: PATCH or X-HTTP-Method-Override: DELETE. This is treated only as a documented fallback, not as the normal API design.

3. Caching and Reliable Retries

3.1 Retry-safety decisions

EndpointPotential problemTechniqueReason
POST /orders The connection can fail after the server has created the order. A client retry could otherwise create a duplicate order or repeat payment-related work. Idempotency-Key The first request associates the key with its result. A repeat using the same key returns the original result instead of performing the operation again.
GET /orders/{id} Repeated reads can transfer and parse the same unchanged representation unnecessarily. If-None-Match A matching ETag allows a 304 response without sending the representation again.
PATCH /orders/{id} Two clients may edit the same order from different versions. If-Match The server accepts the update only when the supplied ETag still represents the current version; otherwise it sends 412.
POST /orders/{id}/cancellation A repeated cancellation may target an order that is already cancelled or has reached a terminal state. 409 / 422 state checks Conflicting lifecycle states and semantically invalid transitions are rejected rather than silently repeated.
Key distinction: Idempotency-key handling is used for order creation because POST is not naturally idempotent. ETags address representation freshness and concurrent-write protection rather than replacing the idempotency mechanism.

5. Assignment Question Responses

Q1. Give three endpoints with their method, successful status and the most important response header.

POST /orders: 201 Created with Location. It gives the client the URI of the newly generated order.
GET /orders/{orderId}: 200 OK with ETag. The tag supports both conditional reads and version-aware updates.
DELETE /orders/{orderId}: 204 No Content with Cache-Control: no-store. A deleted representation should not remain available from an intermediate cache.
Q2. Which endpoints are safe and which are idempotent?

The safe operations are the two GET requests and OPTIONS. GET and OPTIONS are also idempotent. PATCH and DELETE are designed to be idempotent as well. Creating an order with POST is neither safe nor naturally idempotent, so the service uses an Idempotency-Key to make a repeated submission return the original result. Cancellation remains a state-changing POST action and is handled through explicit lifecycle checks.
Q3. Demonstrate ETag use for 304 and 412.

An example service tag is "0aa5da47aa253af6".
A GET containing If-None-Match: "0aa5da47aa253af6" can receive 304 Not Modified, avoiding another representation transfer.
A PATCH containing an outdated value such as If-Match: "stale-etag-99999" receives 412 Precondition Failed, preventing a stale editor from overwriting a newer order version.
Q4. Explain the difference between 400 and 422 using requests.

400 Bad Request: POST /orders with {"customerId":"stu-102"} because required fields such as items and deliveryAddress are missing.

422 Unprocessable Content: POST /orders/{id}/cancellation when the order has already been cancelled or delivered.

The first is a request-structure problem; the second is a validly structured request that cannot be accepted because of the application's current business state.
Q5. Why can a browser block a request even when the server returns 200?

The browser applies the Same-Origin Policy. If the response does not grant the requesting origin permission through CORS, browser-side JavaScript may be prevented from reading the response even though the server itself completed the request. Access-Control-Allow-Origin, together with the appropriate OPTIONS preflight response, supplies that permission.
Q6. Give one cacheable response and one no-store response.

For GET /orders/{id}, the service can use Cache-Control: private, max-age=60 because a browser may reuse a recent private copy while still checking freshness through the ETag mechanism.
For order creation and updates, Cache-Control: no-store is used because these operations change state and should not be replayed from an HTTP cache.
Q7. When would POST be preferable to GET for a search?

POST can be useful when the search expression is very large or structurally complex, such as a deeply nested filter object or a very long collection of IDs. It can also avoid placing sensitive criteria directly in a URL. The trade-off is losing some of the natural GET properties, including straightforward URL bookmarking, link sharing, browser navigation semantics and normal HTTP caching.
Q8. What does Location mean for 201 and 3xx responses?

With 201 Created, Location identifies the newly created resource. With a 3xx redirect, Location identifies the destination URI to which the client should redirect its request.
